## 2. 왜 비용이 이렇게 높은가?

### 2-1. NAT Gateway ($229.34/월) — 가장 큰 낭비

NAT Gateway 비용은 두 가지로 구성됩니다.

- **고정 시간당 요금**: $0.045/시간 × 24h × 30일 = **약 $32.40**
- **데이터 처리 요금**: $0.045/GB

> 남은 **약 $197**는 순수 데이터 전송 처리 비용입니다.

**왜 불필요한가?**

이 브리지 애플리케이션이 NAT Gateway를 통해 통신하는 대상은 다음과 같습니다.

- AWS KMS API (트랜잭션 서명)
- Nine Chronicles 헤드리스 노드 GraphQL (외부 엔드포인트)
- Ethereum/BNB Chain RPC (Infura, Alchemy 등)
- Slack API, OpenSearch, Google Sheets

**하루 트랜잭션이 10건 미만**인데, 이 정도의 데이터 전송량이 월 $197를 발생시키는 것은 비정상적입니다. 거의 대부분이 블록체인 노드와의 **폴링(polling)** 트래픽입니다. EVM 블록 폴링이나 9c 노드 GraphQL 폴링은 퍼블릭 서브넷 인스턴스에서 직접 인터넷 게이트웨이를 통해 처리하면 **데이터 전송 비용이 0에 가깝습니다** (AWS 아웃바운드는 인터넷 게이트웨이 경유 시 수 GB까지 무료).

### 2-2. Application Load Balancer ($74.40/월) — 완전히 불필요

ALB 비용 구성:
- **고정 요금**: $0.008/LCU-시간 × 24h × 30일 ≈ 기본 $16.43
- **LCU 요금**: 실제 트래픽 기반

이 애플리케이션은 **인바운드 HTTP 요청을 받지 않습니다**. 브리지는 순수 아웃바운드 폴링 구조입니다. ALB가 앞에 있더라도 실제 요청이 없으면 존재 자체의 고정 비용만 발생합니다.

**ALB가 필요한 시나리오:**
- 웹 서버나 API 서버처럼 외부에서 HTTP/HTTPS 요청이 들어오는 경우
- 여러 인스턴스에 트래픽을 분산해야 하는 경우

**이 브리지에 ALB가 필요 없는 이유:**
- 인바운드 포트가 없음 (브리지는 외부에서 연결을 받지 않음)
- 단일 인스턴스로 충분 (하루 <10 트랜잭션)
- Health check 대상도 없음

### 2-3. EC2 인스턴스 ($211.89/월) — 과대 프로비저닝

현재 실행 중인 인스턴스가 이 비용을 발생시키고 있습니다. 월 $211의 EC2는 대략 `c5.xlarge` (4 vCPU, 8GB RAM) 또는 그에 준하는 On-Demand 인스턴스입니다.

**실제 필요 스펙:**
- Node.js 프로세스 1개 (TypeScript 브리지)
- SQLite 파일 2개 (`monitor_state.db`, `exchange_history.db`)
- 메모리: 평상시 200–400MB 수준
- CPU: 블록 폴링 시 간헐적 사용, 평균 <1%

결론: **t4g.nano (2 vCPU, 0.5GB RAM)** 또는 **t4g.micro (2 vCPU, 1GB RAM)** 으로 충분합니다.

## 4. t4g.nano vs t4g.micro 비교

| 항목 | t4g.nano | t4g.micro |
|------|----------|-----------|
| vCPU | 2 | 2 |
| 메모리 | 0.5 GB | 1 GB |
| 시간당 가격 (ap-northeast-2) | $0.0042 | $0.0084 |
| 월 비용 | $3.02 | $6.05 |
| 차이 | — | +$3.03 |

**권장: t4g.nano**

Node.js 프로세스 1개의 RSS(Resident Set Size)는 일반적으로 150–350MB입니다. `t4g.nano`의 512MB는 빠듯할 수 있으나, 다음 이유로 충분합니다.

- Linux 커널 + 시스템 데몬: ~100MB
- Node.js 브리지 프로세스: ~200–300MB
- SQLite in-memory 캐시: ~10MB
- 여유 메모리: 50–100MB

만약 운영 중 OOM(Out of Memory)이 발생하면 **무중단으로 `t4g.micro`로 업그레이드** 가능 (인스턴스 타입 변경은 재시작 필요, 약 2분 다운타임).

**스팟 인스턴스는 사용하지 않음**: 스팟 인스턴스는 최대 70% 절감 가능하지만, 언제든 중단될 수 있어 SQLite 파일 손상 위험이 있습니다. 브리지의 상태 저속성(state persistence) 특성상 On-Demand가 안전합니다.

## 5. KMS VPC 엔드포인트 추가 여부 결정 가이드

### 추가가 필요한 경우

- 보안 컴플라이언스상 KMS 트래픽이 인터넷을 경유해선 안 된다는 요구사항이 있을 때
- 프라이빗 서브넷 구조를 유지해야 할 때 (이 경우에는 NAT 대신 VPC 엔드포인트 사용)

### 추가가 불필요한 경우 (현재 시나리오)

- KMS API 통신은 이미 **TLS 1.2+ 암호화**로 보호됩니다
- 퍼블릭 서브넷에서 인터넷 게이트웨이를 통해 KMS에 접근해도 **보안상 문제 없음** (AWS 공식 지원 아키텍처)
- VPC 엔드포인트 비용: **$7.20/월** 추가 발생

**결론: KMS VPC 엔드포인트 추가 불필요**. 퍼블릭 서브넷 + 인터넷 게이트웨이를 통한 KMS 접근은 AWS 표준 아키텍처입니다.
